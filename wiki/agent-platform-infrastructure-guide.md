# Agent 平台基础设施建设指南

> 本文档综合多方视角，梳理 Agent 开发平台从单 agent 本地运行扩展到团队规模化应用时，最重要的基础设施建设方向与优先级。核心目标：**让 Agent 系统的行为从"不可控的黑盒"变成"可观测、可评估、可回滚、可协作的工程系统"**。

---

## 概览：基建层次模型

```
┌──────────────────────────────────────────────────────────────────┐
│                      开发者体验 (DX)                               │
│         本地调试 · 脚手架 · Session Replay · 文档自动生成            │
├──────────────────────────────────────────────────────────────────┤
│               多 Agent 协调层                                      │
│         注册/发现 · 任务调度 · 通信协议 · 资源管理                    │
├──────────────────────────────────────────────────────────────────┤
│        Prompt & Skill 管理  │  工具生命周期管理  │  CI/CD           │
├──────────────────────────────────────────────────────────────────┤
│              评估体系（Evals）                                      │
│       回归测试 · LLM-as-Judge · A/B 对比 · Golden Dataset          │
├──────────────────────────────────────────────────────────────────┤
│              安全与沙箱隔离                                         │
│       权限模型 · 沙箱多 provider · 审计日志 · 输入输出过滤             │
├──────────────────────────────────────────────────────────────────┤
│              可观测性（最底层基础）                                   │
│       分布式追踪 · 结构化日志 · 指标度量 · Execution Graph            │
└──────────────────────────────────────────────────────────────────┘
```

越底层的基建，依赖关系越广、建设越晚越痛苦。

---

## 1. 可观测性（Observability）

**优先级：最高。没有可观测性，后续所有优化都是盲人摸象。**

Agent 系统的核心痛点是**非确定性执行**：同样的 prompt，LLM 可能选择不同的工具调用路径，问题极难复现。

### 1.1 分布式追踪（Tracing）

记录完整的 Agent 执行链路：

```
用户输入
  → prompt 组装（section 渲染）
    → LLM 请求（token in/out，延迟，缓存命中率）
      → 工具调用（参数，执行时间，结果/错误）
        → 子 agent 调度（递归 trace）
          → 最终输出
```

- 每个 span 关联 `session_id`、`trace_id`、`tool_name`、`subagent_type`
- 跨 subagent 的 trace context 传播（`parent_span_id`）
- Bourbon 已集成 OpenTelemetry，需确保 subagent 调用链路不断裂

### 1.2 结构化日志

统一 log schema，禁止裸 `print`：

```json
{
  "ts": "2026-05-12T10:00:00Z",
  "session_id": "sess_xxx",
  "trace_id": "trace_xxx",
  "event": "tool_call",
  "tool": "bash",
  "risk_level": "MEDIUM",
  "duration_ms": 342,
  "tokens_in": 1200,
  "tokens_out": 87,
  "error": null
}
```

### 1.3 指标度量（Metrics）

运营和成本优化的数据基础：

| 指标 | 用途 |
|------|------|
| token 消耗（按 session/feature/subagent 分组） | 成本归因与控制 |
| 工具调用成功率 & 失败分布 | 发现脆弱 tool |
| LLM 请求 p50/p95 延迟 | SLO 设定 |
| 提示词缓存命中率 | 成本优化指导 |
| 子 agent 并发数 | 容量规划 |

### 1.4 Execution Graph 可视化

将 Agent 的决策树可视化：`思考 → 行动 → 观察 → 再思考`，帮助开发者回答"**它为什么会这么做**"。这在调试复杂多步骤任务时价值远超文本日志。

## 2. 评估体系（Evals）

**优先级：次高。Agent 版的"单元测试 + CI"合一。**

传统代码靠单元测试断言正确性，但 Agent 行为由 LLM 驱动，正确性是概率性的。没有持续 eval，每次改动都是"感觉改好了"。

### 2.1 分层测试体系

```
                  ┌─────────────────────────────┐
  慢/昂贵/抽样     │  端到端评估（LLM-as-Judge）  │  promptfoo · A/B 对比
                  └─────────────────────────────┘
                  ┌─────────────────────────────┐
  中速/需外部依赖  │     集成测试（Tool 交互）    │  mock/fixture · sandbox
                  └─────────────────────────────┘
                  ┌─────────────────────────────┐
  快/确定性强      │  单元测试（纯逻辑）          │  prompt 构造 · tool handler
                  └─────────────────────────────┘
```

### 2.2 评估维度

不只是"输出是否正确"，还需评估：

- **功能正确性**：期望行为是否实现
- **工具使用效率**：tool 调用次数、是否有冗余调用
- **成本效率**：完成任务的 token 消耗
- **安全合规**：是否触碰权限边界
- **延迟**：端到端完成时间

### 2.3 Golden Dataset 管理

- Eval cases 像代码一样有 PR Review 和版本记录
- 持续积累真实用户场景（脱敏后）扩充 golden set
- 覆盖度追踪：哪些 feature/tool 有 eval 覆盖，哪些还没有

### 2.4 CI 集成：Eval 作为门禁

```
PR 提交
  → 单元测试（快，必须全过）
    → 核心 eval suite（重点场景回归，必须通过）
      → 完整 eval suite（抽样运行，统计显著性对比）
        → Merge
```

Prompt 或 tool 变更必须附带对应 eval case，否则 PR 不通过。

### 2.5 对抗性测试（Red Teaming）

专门测试边界场景：
- 提示词注入攻击
- 权限绕过尝试
- 超长输入、格式异常输入
- 工具参数边界值

## 3. 安全与沙箱隔离

**优先级：底线工程，不能欠债。**

Agent 拥有代码执行、文件操作、网络访问等能力，一旦失控风险巨大。安全不是可选项。

### 3.1 沙箱层次

```
┌────────────────────────────────────────────────┐
│               应用层权限检查                      │
│   PermissionChecker · risk_level · 人工确认门    │
├────────────────────────────────────────────────┤
│               进程级沙箱隔离                      │
│   bubblewrap(Linux) · seatbelt(macOS) · Docker  │
├────────────────────────────────────────────────┤
│               系统调用过滤                        │
│   seccomp · capability dropping                 │
└────────────────────────────────────────────────┘
```

Bourbon 已支持多 sandbox provider，但需持续加固每层边界。

### 3.2 细粒度权限模型

从"能否执行"细化为"在什么条件下能执行"：

```
条件维度：
  • 操作对象（文件路径范围、网络域名白名单）
  • 执行主体（user agent / subagent 类型）
  • 风险等级（LOW 直接执行，HIGH 需确认）
  • 配额限制（单 session 最大 token、最大文件读写量）
```

**策略即代码（Policy as Code）**：sandbox 策略、权限规则用声明式配置管理，不散落在业务代码里，支持审计和版本回溯。

### 3.3 不可篡改审计日志

记录内容：谁、何时、通过哪个 Agent、执行了什么操作、参数是什么、结果是什么。

- 审计日志写入后不可修改（append-only）
- 支持按 session/user/tool 查询
- 定期归档，保留周期符合合规要求

### 3.4 输入/输出过滤层

- **输入过滤**：检测 prompt injection、异常格式，阻断恶意请求
- **输出审查**：阻止生成恶意代码、敏感信息泄露
- **凭证管理**：API key 安全注入（不出现在 log/trace 里）、定期轮转

## 4. Prompt & Skill 版本管理

**Prompt 是 Agent 的"源代码"，必须工程化管理。**

### 4.1 版本化注册表

```
Prompt Section 生命周期：
  Draft（本地开发）
    → Review（PR 审查 + eval 验证）
      → Staging（灰度验证）
        → Production（全量发布）
          → Archived（历史版本保留）
```

- 每次变更有 diff、commit message、关联 eval 结果
- 支持一键回滚到任意历史版本
- 支持不重启服务的热更新（用于紧急修复）

### 4.2 Prompt 调试工具

能看到实际发送给 LLM 的**完整组装后 prompt**（所有 section 渲染结果），而不只是看各个 section 的源码。这对调试至关重要。

### 4.3 Skill 版本管理

Skill 变更可能影响多个 Agent，需要：
- Skill 的接口（输入/输出格式）变更走兼容性审查
- 新版 Skill 先在隔离环境验证，通过 eval gate 再上线
- 依赖某 Skill 的 Agent 自动触发回归测试

---

## 5. 工具（Tool）生命周期管理

随着 tool 数量增长，管理复杂度指数上升。

### 5.1 Tool 注册与发现

- 统一的 tool catalog：schema、描述、风险等级、依赖声明、owner
- 运行时动态发现（已注册 MCP tools 自动纳入）
- Tool 使用分析：调用频率、失败率、平均耗时——指导优先级排序和淘汰决策

### 5.2 接口稳定性管理

```
Tool 变更分类：
  ■ 向后兼容变更（新增可选参数）→ 直接发布
  ■ 不兼容变更（参数重命名/删除）→ 版本化（v1/v2），双版本共存过渡期
  ■ 行为变更（相同参数，不同语义）→ 必须有 eval 覆盖，灰度发布
```

### 5.3 外部 Tool 健康监控

MCP server 等外部依赖的可用性监控，超时/不可用时的降级策略：
- 重试策略（指数退避）
- 降级替代方案（如 web tool 不可用时返回明确错误而非挂起）
- 健康状态纳入 observability 指标

## 6. 上下文与记忆管理

随着场景复杂，上下文窗口管理和记忆质量成为瓶颈。

### 6.1 记忆分层架构

```
┌─────────────────────────────────────────────┐
│   长期记忆（用户画像 · 项目知识 · 跨会话）      │  持久化存储，语义检索
├─────────────────────────────────────────────┤
│   中期记忆（会话摘要 · Task 上下文）            │  压缩后保留，结构化
├─────────────────────────────────────────────┤
│   短期记忆（当前对话 · 工具调用结果）            │  in-memory，上下文窗口内
└─────────────────────────────────────────────┘
```

### 6.2 压缩策略工程化

上下文压缩不应该是"超限就压"的粗暴策略，而需要：
- **优先级感知**：系统 prompt、当前任务上下文、近期工具结果保留，远期闲聊可压缩
- **语义保全**：压缩后关键事实不丢失（可用 eval 验证）
- **压缩质量度量**：压缩前后关键信息召回率

### 6.3 记忆质量评估

记忆写入是否准确、召回是否相关，需要量化指标，而不是主观感觉好用。

## 7. 多 Agent 协调层

从单 Agent 到多 Agent 是复杂度的跃迁节点，需要系统性设计。

### 7.1 Agent 注册与发现

```
Agent Registry：
  agent_id: "code-reviewer"
  capabilities: ["code_review", "static_analysis"]
  tool_access: ["read_file", "bash"]
  sandbox: "bubblewrap"
  status: "healthy"
  instance_count: 3
```

统一目录，支持按能力动态路由，而不是硬编码 agent 类型。

### 7.2 任务调度与状态机

```
Task 状态流转：

  PENDING → RUNNING → COMPLETED
                 ↓         ↓
              FAILED    CANCELLED
                 ↓
              RETRYING
```

- 支持 Agent 间任务委派、并行执行、结果聚合
- 任务优先级队列，防止关键任务被低优任务饿死
- 超时控制与取消机制

### 7.3 共享状态与冲突解决

多 Agent 并发操作同一资源时：
- 乐观锁（CAS）适用于低冲突场景
- 任务级互斥锁适用于危险操作（如同一文件写操作）
- 共享只读资源（如记忆库）使用读写锁

### 7.4 通信协议

Agent 间传递：
- **任务上下文**：完整的任务描述和当前状态
- **部分记忆**：与任务相关的记忆片段（而非全量）
- **结果格式约定**：统一的成功/失败/部分完成返回结构

## 8. CI/CD 与发布流程

Agent 项目的 CI/CD 比传统软件更复杂，需要 AI-aware 的流水线。

### 8.1 Prompt-Aware CI

```
代码变更 PR
  ├── 影响范围分析
  │     ├── 仅代码逻辑变更 → 常规测试套件
  │     ├── Prompt/Skill 变更 → 触发 eval suite
  │     └── Tool 接口变更 → 触发兼容性测试 + 依赖 Agent 回归
  ├── 评估结果对比（与 baseline 比较，统计显著性）
  └── 审批 & 合并
```

### 8.2 渐进式发布

```
Canary（1%流量）
  → 小范围灰度（10%）
    → 全量发布
      → 持续监控（异常自动回滚）
```

- 新 Prompt/Tool 版本先对部分用户/会话生效
- 基于 observability 指标（错误率、成本、延迟）自动决策是否继续
- 出现异常指标时自动触发回滚

## 9. 开发者体验（DX）

基建不只服务线上，更要服务开发者。DX 是团队协作效率的乘数。

### 9.1 Session Replay（最关键的 Agent 调试工具）

能够回放任意历史 session，逐步查看：
- 每个时刻的完整 prompt 内容
- LLM 的 reasoning 和 tool 选择过程
- 工具执行参数与结果
- 上下文窗口的当前状态

这是 Agent 调试最缺失的能力，传统 debugger 无法胜任。

### 9.2 本地开发环境标准化

- 一行命令启动完整开发环境（含 mock 外部依赖）
- 本地环境与生产环境行为一致（配置驱动，而非硬编码）
- 快速创建新 Tool/Skill/Eval case 的脚手架模板

### 9.3 文档自动生成

Tool schema、Prompt section 描述、配置项说明应从代码/注解自动生成，不手动维护（否则必然过时）。

### 9.4 贡献指南

新加入团队成员的标准路径：
1. 用脚手架创建新 Tool，跑通本地测试
2. 写配套 eval case
3. 走 PR 流程（eval gate 验证）
4. 上线后用 observability 验证符合预期

## 优先级与演进路线

### 按团队阶段的建设重点

| 阶段 | 团队规模 | 重点建设 | 核心目标 |
|------|---------|---------|---------|
| **起步期** | 1-2 人 | 可观测性（OTel tracing + 结构化日志）+ Eval 框架（CI 集成） | 能看清 Agent 在做什么，改了东西有回归保护 |
| **成长期** | 3-5 人 | Prompt/Skill 版本管理 + Session Replay + Tool 生命周期管理 | 多人协作不踩坑，出问题能快速定位 |
| **规模期** | 5+ 人 | 多 Agent 协调层 + 渐进式发布 + 成本归因 | Agent 作为服务提供，质量稳定，成本可控 |

### Bourbon 现状对照

| 基建领域 | Bourbon 现状 | 主要缺口 |
|---------|------------|---------|
| 可观测性 | OTel tracing（元数据级） | 成本归因、行为分析 dashboard、按 feature 分组 |
| 评估体系 | promptfoo eval + pytest | CI 集成为门禁、eval case 覆盖度追踪 |
| 安全沙箱 | 多 provider 沙箱 + 权限检查 | Policy as Code、不可篡改审计日志 |
| Prompt 管理 | PromptBuilder + 有序 section | 版本化注册表、热更新、完整 prompt 调试视图 |
| 记忆系统 | 本地语义索引 + 混合检索 | 记忆质量评估指标、跨机器持久化 |
| 多 Agent | SubagentManager（进程内） | Agent 注册发现、异步任务队列 |
| CI/CD | pytest + ruff + mypy | Eval 作为 CI gate、渐进式发布 |
| DX | Rich REPL | Session Replay、脚手架工具 |
