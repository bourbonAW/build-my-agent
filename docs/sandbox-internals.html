// 01 · Overview

隔离技术谱系总览

所有 sandbox 工具在"共享宿主内核 ↔ 独立内核"这条轴上占据不同位置。隔离强度越高，攻击面越小，但启动开销也越大。

// 02 · Fundamentals

核心 Syscall 体系

所有 Linux sandbox 工具共享同一套内核接口。差异在于用了哪些 syscall、以何种顺序调用、哪一层来调用。

// FIG.02 — 所有 Linux sandbox 工具共享的 syscall 全集，按功能层分组。KVM 层仅被 Firecracker/Kata 使用。

关键心智模型：Namespace 决定进程能"看到"什么；Capabilities 决定进程名义上"能做"什么；Seccomp 决定内核是否"接受"该 syscall。三层各自独立，需同时配置才能形成完整防御。
// 03 · Bubblewrap

Bubblewrap (bwrap)

bwrap 是一个用户态编排器，自身不实现任何隔离逻辑，只负责按正确顺序将 namespace syscall 发出给内核。核心能力来自 Linux 3.8 引入的 CLONE_NEWUSER——它让非 root 用户也能创建隔离容器。

// FIG.03 — bwrap 完整启动链路（bourbon BwrapProvider 生成的参数对应每一步）

CLONE_NEWUSER 的意义：Linux 3.8 起，普通用户可调用 clone(CLONE_NEWUSER) 而无需任何 capability。内核允许在 user namespace 内拥有 uid=0（容器内"root"），但宿主层面映射回普通用户权限——这是 unprivileged sandbox 的基石。
// 04 · Docker / runc

Docker / runc

runc 是真正的容器运行时。Docker CLI → dockerd → containerd → runc 调用链最终落到 runc，由它执行 namespace + cgroup + OverlayFS 的全套配置。相比 bwrap 多了两个关键能力：cgroup 资源硬限制和OverlayFS 分层文件系统。

// FIG.04 — OverlayFS 分层结构。容器删除时 upperdir 销毁，lowerdir 永久共享。

bourbon DockerProvider 的安全配置

docker run --rm \
  --cap-drop=ALL                      # capset() 撤销全部 Linux capabilities
  --security-opt no-new-privileges    # prctl(PR_SET_NO_NEW_PRIVS, 1)
  --user nobody                       # setuid/setgid 到非特权用户
  --memory 512M                       # cgroup: write(".../memory.limit_in_bytes", 536870912)
  --network none                      # CLONE_NEWNET → 空网络栈，无路由
  -v /workdir:/workdir:rw             # 可写路径
  -v /readonly:/readonly:ro           # 只读路径
  # DENY 路径: 不挂载 → 容器 rootfs 中不存在该路径
  python:3.11-slim bash -c "command"
// 05 · gVisor

gVisor — 用户态内核

gVisor 的核心思想是在应用和宿主内核之间插入一个 Go 实现的用户态内核（Sentry）。应用的 syscall 不直接到宿主内核，而是被 Sentry 接管处理，宿主内核暴露的攻击面从"全部 300+ syscall"缩减到约 100 个。

// FIG.05 — gVisor Systrap 拦截机制。Sentry 是用 Go 实现的用户态内核，位于应用与宿主内核之间。

// 06 · Firecracker

Firecracker — KVM MicroVM

Firecracker 完全不用 namespace 路线，转而使用硬件虚拟化。每个沙盒拥有独立的 Linux 内核实例，Guest 的 syscall 完全在 Guest 内核内处理，永远不会以 syscall 的形式到达宿主内核——宿主只看到 KVM 的 VM-exit 事件。

// FIG.06 — Firecracker KVM 启动链路。Guest syscall 在 Guest 内核内完整处理，宿主内核对 Guest 行为不可见。

// 07 · macOS Seatbelt

macOS Seatbelt

seatbelt 完全不走 Linux namespace 路线。底层是 XNU 内核的 MACF（Mandatory Access Control Framework）——在每一个安全敏感系统调用上安装 hook，由 Sandbox.kext 进行策略评估。

// FIG.07 — macOS seatbelt MACF Hook 评估链路。"最后规则胜"的 SBPL 规则顺序是 bourbon SeatbeltProvider 的设计依据。

bwrap

核心: clone(CLONE_NEW*)

靠 namespace 切割内核资源视图，无法限制资源用量，不做 capabilities 管理。

runc

核心: clone + mount(overlay) + write(cgroup)

namespace + 分层 FS + 资源配额，bourbon DockerProvider 的完整防御还需补 seccomp。

gVisor

核心: seccomp(SECCOMP_RET_TRAP) + SIGSYS

用户态内核接管，宿主攻击面从 300+ 缩减至 ~100 个 syscall。

Firecracker

核心: ioctl(KVM_CREATE_VM) + ioctl(KVM_RUN)

硬件虚拟化，物理隔断内核边界，Guest syscall 永不触达宿主内核。

// 10 · OpenSandbox

OpenSandbox 在此坐标中的位置

OpenSandbox（11.3k stars，CNCF Landscape）定位为"Secure, Fast, and Extensible Sandbox runtime for AI agents"，直接将运行时替换为社区主流解法。

架构

运行时可插拔

SDK → FastAPI server → execd/ingress/egress → 运行时层（runc / gVisor / Kata+Firecracker）。平台配置，应用透明。

安全

明确支持 MicroVM

~/.sandbox.toml 中切换运行时，底层使用 Kata+Firecracker 实现 ~125ms 冷启动的硬件级隔离。

性能

Pool 预热 + O(1) 批分配

K8s Controller 预创建沙盒实例，BatchSandbox 用单次 annotation 写入完成批量分配，消除冷启动延迟。

注意

快照组件需节点权限

Pause/Resume 快照需挂载宿主 containerd socket，该组件本身具有节点级权限，生产部署需单独审查。
